# План проверки и автоматизации приложения «Мобильный хоспис»

Версия плана: 1.0.

## 1. Цель

Определить границы приложения, проверить доступные пользовательские сценарии,
подготовить воспроизводимые проверки и выбрать кандидатов на UI-автоматизацию.
Проверки перечислены в `Check.csv`, подробные сценарии — в `Cases.csv`.

## 3. Границы

В проверку входят:

1. Запуск, авторизация, ошибки ввода и сети, сохранение сессии и выход.
2. Главная страница: блок последних новостей, раскрытие, ссылка на все новости.
3. Новости: карточки, обновление, сортировка, фильтр категории и периода, пустые результаты.
4. Права доступа к панели управления новостями.
5. Панель управления: метаданные, сортировка, фильтр активности.
6. Создание, изменение, активность и удаление собственных тестовых новостей.
7. Раздел «Наша миссия»: восемь информационных карточек и навигация.
8. Возобновление приложения, поворот, локали, увеличенный шрифт, доступность элементов.

Не входят: не представленные в навигации заявки, регистрация и восстановление
пароля, медицинские процессы, серверная нагрузка, проверка серверного исходного
кода, полноценный аудит безопасности, все устройства и все версии Android.
Наличие старых строк и макетов комментариев не означает наличия доступного сценария.

Основная роль — учебный пользователь из задания. Административные операции
выполняются только после подтверждения доступности панели. Для отрицательного
сценария прав нужна отдельная предоставленная учётная запись без admin.

## 4. Виды тестирования и подход

| Вид | Содержание |
| --- | --- |
| Smoke | Установка, запуск, корректный вход, главная, новости, панель, выход |
| Функциональное | Навигация, фильтры, сортировка, CRUD новостей, сессия |
| Негативное | Пустые и пробельные поля, неверные данные, неполный период |
| Граничные значения | Обе даты равны, крайние минуты суток, начало и конец периода |
| Интеграционное через UI | Вход, загрузка и сохранение на учебном backend, повторное чтение после обновления |
| Устойчивость | Нет сети, восстановление, повторные нажатия, фон и возврат, поворот |
| Совместимость | В первую очередь Android 16 / API 36, затем при необходимости другие API |
| Интерфейс и доступность | ru/en, шрифт 100%/130%, клавиатура, системные панели, TalkBack |
| Регрессионное | Повтор P0/P1 после изменений приложения и уточнения требований |

Используются классы эквивалентности, граничные значения, сочетания фильтров,
переходы состояний «вход/выход» и «активна/неактивна», исследовательские проверки.
Ожидаемые результаты в кейсах — исходные проверяемые ожидания; неоднозначные
правила вынесены в вопросы ниже. Отсутствие согласованного лимита длины поля
не позволяет придумывать точное максимальное значение.

## 5. Окружение и тестовые данные

- Основное окружение: выделенный Android Emulator, Android 16 / API 36, x86_64,
  портретная ориентация, ru-RU, часовой пояс Europe/Moscow, автоматическая дата.
- Сборка debug из исходников этой копии, Gradle Wrapper 8.13, AGP 8.12.2,
  JDK 17 или совместимый JDK Android Studio. Установлены необходимые SDK/build-tools.
- Интернет для учебного backend и первого скачивания зависимостей. Неполадки
  загрузки SDK или зависимостей фиксируются отдельно от дефектов приложения.
- Учебные данные для входа берутся из задания. Пароли, токены и локальные
  пути SDK в публичный Git не записываются.
- Данные для CRUD: уникальный префикс `QA_DIPLOMA_<дата-время>`, известные категория,
  заголовок, описание, статус, дата и время. Записать уникальный заголовок и поля.
  Изменять и удалять только собственные записи. Очистка обязательна после каждого
  сценария, в том числе после неудачного выполнения. Серверный ID в интерфейсе
  не отображается и через UI не проверяется; записи различать по уникальному
  заголовку и подготовленным значениям полей.
- Для фильтров и сортировки заранее подготовить известные положительные и
  отрицательные записи с различными датами, категориями и статусами. Не опираться
  на случайное содержание общей ленты и не удалять чужие новости ради пустого списка.
- Для времени использовать дату устройства с явно зафиксированным часовым поясом.
  Будущая публикация проверяется на следующий день, без ожидания до наступления даты.
- Сброс данных допустим только у выделенного тестового экземпляра. Для проверки
  сохранения сессии данные приложения не очищать.

## 6. Формат чек-листа и тест-кейсов

Оба CSV используют разделитель `;`, кодировку UTF-8 с BOM, стандартное CSV-экранирование.
В Excel при необходимости выбрать импорт текста с разделителем «точка с запятой».
В `Check.csv` краткие проверки `CHK-NNN` связаны с подробными `TC-NNN` в `Cases.csv`.
Кейсы содержат предусловия, данные, шаги, ожидаемый и фактический результат,
окружение, дату, доказательства и план автоматизации.

Статусы выполнения:

- `Пройден` — сценарий выполнен, фактический результат соответствует ожидаемому.
- `Не пройден` — выполнен и обнаружено расхождение, описанное в строке.
- `Не выполнялся` — полный сценарий ещё не выполнен или его результат не подтверждён.
- `Заблокирован` — выполнить нельзя из-за указанной зависимости или среды.

Отсутствие устройства — не провал функции. Чтение кода, сборка и наличие resource ID
не дают права поставить пользовательскому сценарию `Пройден`.
Для параметризованных строк записывать результат каждого варианта; общий успех
допустим только при успешном выполнении всех вариантов.
При сбое описывать экран, действия, ожидание, факт и условия повторения,
прикладывать очищенные от паролей и токенов доказательства. Случайный сетевой сбой
сначала перепроверить, не записывать его автоматически как дефект клиента.

## 7. План UI-автоматизации

Сейчас UI-тесты не реализованы. В колонке «Автоматизация UI» это указано явно;
«План покрытия» означает только намерение, не наличие тестового кода.

Стек: Kotlin, AndroidX Test/JUnit4, Espresso, Espresso Intents; для действий
с системными настройками — UI Automator при необходимости. Проект уже содержит
зависимости AndroidX Test, но их наличие не означает наличие тестов.
Для Allure Android потребуется проверить совместимость с выбранными версиями инструментов.

Архитектура будущих тестов: классы экранов с действиями и проверками, отдельные
объекты элементов, фабрика уникальных тестовых данных, явная подготовка и очистка.
Тесты независимы, не требуют порядка запуска. Имена описывают действие и результат,
например `loginWithValidCredentialsOpensMainScreen`.
Поля искать по resource ID, подписи — по строковым ресурсам, а не координатам.
Ожидания завершения загрузки реализовать через IdlingResource или проверяемое
состояние, без фиксированных длинных sleep. Секреты получать из локальной
конфигурации вне Git или защищённых переменных CI, не сохранять в отчётах.

Порядок автоматизации: P0 smoke → P1 авторизация и новости → CRUD и права →
негативные фильтры → жизненный цикл и часть интерфейсных проверок.
На API 36 потребуется прогон на чистом тестовом окружении. Зелёный результат
на другом API не заменяет этот прогон. Проверки на живом учебном сервере
отделить от контролируемых проверок ошибок и сетевых тайм-аутов.

Понятность перевода, озвучивания TalkBack и полную визуальную оценку оставить
ручными, хотя отдельные технические свойства можно автоматизировать.
Причина неполного покрытия указана у соответствующих кейсов.
Строгие ожидаемые результаты неподтверждённых правил автоматизировать только
после согласования. Для роли без admin автоматизация возможна, но пока нужны данные.

## 8. Риски и неуточнённые требования

1. Доступность и общее состояние учебного backend: чужие записи меняются,
   возможны задержки и ограничения. Нужны уникальные данные и очистка.
2. Доступ учебной учётной записи к панели управления подтверждён в TC-034.
   Для отрицательной проверки прав нужна отдельная учётная запись без admin.
3. Каков согласованный результат для обратного диапазона дат? В просмотренном
   обработчике проверяется наличие обеих дат, явная проверка их порядка не найдена.
   До уточнения не объявлять дефектом конкретное сообщение или пустой список.
4. Как должен работать фильтр панели, если сняты оба статуса? Код трактует оба
   включённых и оба выключенных флага как отсутствие ограничения. Требование
   для обоих выключенных флагов уточнить до строгого кейса.
5. Уточнить ограничения длины и допустимых символов заголовка/описания, правила
   публикации задним числом и требование сохранять черновик при Back/повороте.
6. Запуск на API 36 проверен на одном эмуляторе. Это не подтверждает работу на всех
   устройствах и во всех сочетаниях системных настроек.
7. Список известных функций составлен по исходникам предоставленного приложения,
   отдельной полной функциональной спецификации в задании нет.

44 задачи выполнены. В исходном проекте остаются предупреждения об устаревших API
и экспериментальных корутинах; поведение приложения не изменялось.

APK установлен на выделенный эмулятор `QA_Diploma_API_36`: Android 16 / API 36,
x86_64, профиль Pixel 6, 1080×2400, en-US, Europe/Moscow. Выполнена интерактивная
проверка интерфейса с помощью ADB, скриншотов и дерева UI. Это не реализованный
набор UI-автотестов и не измерение времени ручного прогона человеком.
Русская локаль и другие профили устройств пока не проверены.

В таблицах 64 сценария: 31 пройден, 1 не пройден, 2 заблокированы,
30 не выполнены полностью. Частичные наблюдения не отмечены как успешный прогон.
Для отрицательной проверки прав нет отдельной учётной записи без admin.
В AOSP-образе отсутствует TalkBack, поэтому озвучивание не проверено.

**BUG-001 — неверная дата создания новости.** У собственной записи
`QA_DIPLOMA_20261021_0526`, созданной 21.10.2026, в панели отображается
`Creation date = 03.01.58775`. Ожидается 21.10.2026. Дата публикации 21.10.2026
отображается корректно. Расхождение сохраняется после повторной загрузки панели.
Воспроизведение: войти → Новости → Панель управления → создать новость с уникальным
заголовком и датой публикации сегодня → найти карточку и проверить дату создания.
Серьёзность — средняя, причина в клиенте или сервере не установлена.
Зафиксировано как `Не пройден` в TC-036 / CHK-036.

Проверены создание, отключение и включение активности, отмена редактирования
и подтверждённое удаление собственной тестовой записи. Проверка изменения всех
полей одним сценарием ещё не завершена. Тестовая запись удалена, отсутствие
подтверждено повторной загрузкой панели и общей ленты.

Одноразовые скриншоты и очищенные от значений пароля деревья UI сохранены локально
во временной папке ОС `qa-diploma-stage1-20261021`, в репозиторий не включены.
В CSV приведены имена соответствующих наблюдений и текст фактического результата;
эти имена не являются ссылками на опубликованные вложения.
