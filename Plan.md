# План проверки и автоматизации приложения «Мобильный хоспис»

## Цель и основания

Проверить пользовательские сценарии Android-приложения и выделить критичные проверки
для повторяемой UI-автоматизации. Основания: задание диплома и
[исходный проект Netology](https://u.netology.ru/backend/uploads/lms/content_assets/file/16394/fmh_android_updated.zip).
Исходники находятся в [app](app). Версия: `1.0.0` (`14`), пакет `ru.edu.qamid`.
Перечень сценариев определяется по доступной навигации, ресурсам экранов и исходникам;
отдельной полной функциональной спецификации задание не содержит.

[Check.xlsx](Check.xlsx) содержит чек-лист, [Cases.xlsx](Cases.xlsx) — подробные кейсы.
Дефекты оформляются в [Bugs.xlsx](Bugs.xlsx), результаты — в [Result.md](Result.md).

## Границы проверки

- Установка и запуск, авторизация, валидация полей, сессия и выход.
- Читаемость введённого логина и маски пароля в светлой и тёмной темах.
- Главная страница: последние новости, раскрытие блока, переход ко всем новостям.
- Новости: раскрытие карточек, обновление, сортировка, фильтр по категории и датам.
- Панель управления: доступ, метаданные, фильтры активности, сортировка.
- Создание, изменение, переключение активности и удаление собственных новостей.
- Информационный экран «Наша миссия»: восемь карточек с цитатами.
  Отдельного экрана «О приложении» в навигации предоставленной версии нет.
- Возврат из фона, поворот, локали, увеличенный шрифт, системные панели и доступность.

Вне области: медицинские процессы, серверная нагрузка, исходники backend,
непредставленные в навигации заявки, регистрация, восстановление пароля,
полный аудит безопасности, все устройства и версии Android.
Наличие устаревшего макета в исходниках не считается доступным пользовательским сценарием.

## Виды тестирования и тест-дизайн

| Вид | Проверки |
| --- | --- |
| Smoke | Установка, запуск, вход, главная, новости, панель управления, выход |
| Функциональное | Навигация, сортировка, фильтры, CRUD собственных новостей |
| Негативное | Пустые и пробельные поля, неверные данные, неполный период |
| Граничные значения | Одинаковые даты начала/конца, начало и конец периода, крайние минуты суток |
| Интеграционное через UI | Вход и сохранение на учебном backend, повторное чтение записи |
| Устойчивость | Потеря/возврат сети, повторные нажатия, фон, перезапуск, поворот |
| Совместимость | Android 16 / API 36, ru/en, светлая/тёмная тема, шрифт 100%/130%, системные панели |
| Доступность | Названия элементов, порядок фокуса и озвучивание TalkBack |
| Регрессионное | Повтор критичных сценариев и сценариев найденных дефектов |

Использовать классы эквивалентности, границы диапазонов, комбинации фильтров и
переходы состояний «вход/выход», «активна/неактивна». Для параметризованной проверки
фиксировать каждый вариант. Не придумывать точные лимиты полей без требований.

## Окружение и данные

- Android Emulator: Android 16 / API 36, x86_64, профиль Pixel 6, 1080×2400,
  портретная ориентация; основная локаль en-US, дополнительная ru-RU;
  Europe/Moscow, корректные дата и время.
- Debug-сборка: Gradle Wrapper 8.13, Android Gradle Plugin 8.12.2,
  JDK 17, compileSdk/targetSdk 36, minSdk 23. Интернет нужен для зависимостей и backend.
- Учебный backend: `https://students.netoservices.ru/qamid-diplom-backend/`.
- Учётная запись из задания передаётся через параметры запуска или локальную
  конфигурацию, указанную в `.gitignore`. Пароль и токены не записывать в отчёты.
- Собственные новости имеют уникальный префикс `QA_DIPLOMA_` и известные значения
  полей. Для сортировки/фильтров подготовить записи с различными датами и категориями.
  Для будущей публикации выбирать известную дату без ожидания её наступления.
- Изменять и удалять только собственные данные; предусмотреть очистку при ошибке теста.
  Сохранять ID подтверждённо созданной записи для очистки, если она станет недоступна
  в загруженной части списка. Резервное удаление выполнять только для зарегистрированных
  ID; неизвестный результат сохранения или очистки отражать явно.
  Постоянные ожидаемые значения не брать из случайного содержимого общей ленты.
  Для проверки сброса фильтра допустимо запомнить существующую опубликованную запись,
  считая её наличие предусловием. Очистка чужих новостей ради проверки пустого списка недопустима.
- Для проверки прав нужна отдельная учётная запись без admin. Сетевые настройки
  менять только у выделенного эмулятора и восстанавливать после сценария.

## Подход к автоматизации

Стек: Kotlin, AndroidX Test, JUnit4, Espresso, Allure Android.
Классы разделять по функциональности: авторизация, новости, информационные экраны.
Действия и проверки элементов инкапсулировать в Page Objects; тесты описывают сценарий
вызовами этих объектов. Имена отражают действие и результат.
Локаторы хранить полями соответствующих Page Objects. Тестовые классы размещать
в отдельном пакете `tests`. Данные новости передавать единым объектом с именованными
полями: категория, заголовок, описание, дата и время публикации, статус.
Не дублировать значения тестовых данных между подготовкой, действиями и проверками.
Для изолированных проверок редактирования и удаления выбирать собственные будущие
публикации с известными значениями. Доступность новости с текущей датой публикации
после повторного чтения проверять отдельным сценарием.

Тесты независимы от порядка запуска. Каждый сценарий готовит исходное состояние,
использует уникальные данные и очищает их. Элементы искать по resource ID и строковым
ресурсам; для карточек использовать уникальный заголовок собственной записи.
Применять IdlingResource или ограниченное ожидание проверяемого состояния, без `sleep()`.
Отсутствие элемента проверять после завершения загрузки.
При повторном открытии панели дожидаться завершения обновления и применения свежих
данных в адаптере. Непустой локальный кэш сам по себе не подтверждает чтение с сервера.

Автоматизировать вход с корректными/некорректными данными, выход, базовую навигацию,
обязательное создание, редактирование и удаление собственной новости,
валидацию, информационные экраны и проверку, воспроизводящую дефект.
Не подменять ожидаемый результат фактическим ради зелёного отчёта.
В Allure добавлять понятные имена, feature/story, severity, шаги и безопасные вложения
при ошибке. Сбой окружения отличать от дефекта приложения.

Качество перевода, полную визуальную оценку и удобство озвучивания оставить ручными.
Причины неполного покрытия и связь с тестовыми методами указывать в Cases.xlsx.

Для обычного текста поля авторизации выбрать проверяемый критерий читаемости:
отношение контраста текста и фона не ниже `4,5:1` в обеих темах. Основание —
[WCAG 2.2, SC 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html),
источник проверен 26.10.2026. Это выбранный критерий QA, а не отдельное требование
исходного задания. Дополнительно проверить снимок экрана и сохранение введённого
значения, чтобы отличить нечитаемый текст от потери данных.

## Порядок и критерии проверки

1. Проверить зависимости и собрать приложение и тестовый APK.
2. Установить на выделенный API 36, проверить доступность backend и учётной записи.
3. Выполнить smoke и приоритетные функциональные проверки; фиксировать результаты
   в чек-листе, расхождения оформлять в Bugs.xlsx со ссылкой из кейса.
4. Запустить независимые UI-тесты; сохранить Allure и разобрать каждый сбой.
5. Сравнить одинаковый набор сценариев при ручном и автоматическом выполнении.
   Измерять отдельно подготовку, сам прогон и анализ результатов; не сравнивать
   весь чек-лист с меньшим набором автотестов как эквивалентные объёмы.

Критерий готовности: сборка воспроизводима, запуск на API 36 подтверждён,
обязательные UI-сценарии реализованы, каждый сбой объяснён и связан с дефектом
или ограничением; документация содержит точные команды и реальные результаты.
Незапущенная или частично выполненная проверка не считается успешной.

## Риски и неуточнённые требования

- Общий backend и изменяемая лента: использовать уникальные данные, учитывать задержки.
- Роль без admin требует отдельной предоставленной учётной записи.
- Не определён ожидаемый результат обратного диапазона дат и снятия обоих статусов
  в фильтре панели. Не объявлять конкретное поведение дефектом без требования.
- Требуют уточнения лимиты длины/символов полей, публикация задним числом,
  сохранение черновика при Back/повороте.
- Нужен образ с TalkBack для проверки озвучивания. Один эмулятор API 36
  не подтверждает работу на всех устройствах и системных конфигурациях.
